## Actual reports

Version **0.5.0**, measured 23 September 2026, passes the listed local CPU/GPU workloads on both physical targets with zero bitwise word differences. Final capacity runs complete **12,244,544 GTX states** and **14,569,792 POCO states**, each for two epochs under a stated memory policy. Three-sample GPU medians at 4,096 states × 64 epochs are **0.157167648 seconds** and **0.1693103924 seconds**, respectively. These scoped results do not change the missing-architecture or unproved-claim rows above.

For current v0.5 status, use `docs/VALIDATION_v0.5.md` and the identified raw records under `results/v0.5/`. This includes corrected-arithmetic GTX comparisons with zero bitwise word differences and separately identified phone outcomes. Older v0.4 results remain in `results/v0.4/VALIDATION.md` and `results/v0.4/summary.json`, including GTX epoch-96 and POCO epoch-1 failures. The first trig-only v0.5 candidate also failed at GTX epoch 305; it is not the corrected division/square-root candidate. Successful finite comparisons are not arbitrary-horizon or all-device equivalence. S07 establishes the stated discrete position/orientation wrapping; smooth Klein tangent covariance and asymmetric operator-frame transport remain unestablished.

Generated summaries, individual JSON reports and command stdout/stderr describe their recorded build. The packaged `results/STATUS.md` indexes the current v0.5 campaign; the previous root status is preserved as `results/v0.4/historical_root_STATUS.md`. The corrected-arithmetic existing-suite result is `results/v0.5/claims_corrected/summary.json`; final-artifact physical-device records and suite results are under `results/v0.5/2026-09-23/`. A failed run remains failed. An unavailable device or unsuccessful pipeline build cannot be assigned a successful execution outcome.

`tools/run_claims.py --device "1650 Ti"` performs the desktop device run without allowing a software ICD. `tools/test_phone.py` launches the actual Android application through an authorized ADB connection and retrieves its numerical and device reports. It records Android system RAM and thermal status separately from Vulkan memory heaps; the phone's 12 GB system RAM is not treated as 12 GB dedicated VRAM.

Version 0.5 uses actual integer LUT images, packed one-bit controls and full FP32 parameters. Four-bit scalar bytecode remains necessary for the current vocabulary. The 1,984-byte shared core LUT describes per-workgroup storage; it does not establish S10's permanent-cache claim. `tools/measure_capacity.py` and `tools/measure_phone_capacity.py` measure full-population updates under explicit memory policies. Healthy completion establishes tested capacity, while all-word CPU/GPU comparison is a separate accuracy result. A kernel timestamp excludes setup/readback; a complete-process timer includes them. Neither is a FLOPS, occupancy, bandwidth or cache-hit measurement.

The staged ARM schedule uses eight dependent evolution dispatches per partition and bounded device scratch; it retains the same logical mutation/evolution recurrence. Actual phone `verify` results compare CPU and GPU from a common local snapshot. Initialization still uses host-native math, so equal CLI seeds/configuration on Windows and Android do not guarantee equal initial FP32 words. Cross-device bitwise replay requires an identical imported checkpoint/initial payload and a separate comparison. Zero phone validation counters are meaningful as a layer result only when the report also says its validation layer was enabled.

## Reading numerical operator coverage

The suite changes each active operator body and compares a **state-only digest**, not merely a digest containing the edited instruction word. A numerical-state change establishes that the edited definition participates in the circulation. Indices 25 (Bayer) and 26 (BC5) are deliberately tested in downstream tools rather than fed into the core. The full state-and-operator digest is separately used for exact same-environment checkpoint replay.

## Physical-observation interface

`tools/evaluate_experiment.py` accepts three explicit CSV files: observed detector counts, candidate expected counts, and reference expected counts. It computes descriptive Poisson-deviance scores at identical supplied positions. No observations are fabricated. A lower score for one supplied prediction would be a result about that dataset and its experimental design, not an automatic proof of a universal physical claim.

## Numerical counterexamples are results

The suite deliberately includes successful tests whose result is a counterexample: inverse transforms do not automatically delete added noise; scaled scalar fields need not be exact metric SDFs; pointer removal only saves pointers actually present; and a fixed b-bit store cannot losslessly encode all longer arbitrary strings. These tests concern specific statements in the source discussion, not a blanket verdict on the Dawnwood architecture.
